# Информационная система управления объектами

Веб-приложение для управления объектами предметной области (билеты и связанные сущности)
с хранением данных в PostgreSQL и синхронизацией состояния между всеми клиентами.

## Основные возможности

### Управление объектами

Каждая операция выполняется **в отдельном окне (интерфейсе)** приложения:

- **Создание** нового объекта — с возможностью сразу связать его с уже существующими
  в системе объектами вспомогательных классов.
- **Просмотр** объекта по ID — вместе с информацией о всех связанных объектах.
- **Обновление** атрибутов объекта — в отдельном диалоговом окне.
- **Удаление** объекта.

> Все операции выполняются на **серверной стороне**, изменения
> синхронизируются с базой данных.

### Каскадное удаление

Если удаляемый объект связан с другими объектами, связанные объекты **переносятся
на другой объект по выбору пользователя**, после чего исходный объект удаляется.

### Главный экран

- Список текущих объектов в виде таблицы: **каждый атрибут — отдельная колонка**.
- **Пагинация**, если объекты не помещаются на одном экране.
- **Сортировка** по любой из колонок.
- **Фильтрация** по значениям любой строковой колонки — по *неполному* совпадению.
- Переход к редактированию объекта возможен как из общей таблицы,
  так и из области визуализации объекта (при её реализации).

### Синхронизация между клиентами

При добавлении, изменении или удалении объекта он должен автоматически
появиться, измениться или исчезнуть в интерфейсах **всех остальных**
авторизованных пользователей — без перезагрузки страницы.

## Специальные операции

Для них реализуется **отдельный пользовательский интерфейс**.

| № | Операция |
| --- | --- |
| 1 | Удалить один (любой) объект, у которого значение поля `comment` равно заданному |
| 2 | Вернуть один (любой) объект с максимальным значением поля `venue` |
| 3 | Вернуть массив уникальных значений поля `number` по всем объектам |
| 4 | Создать новый билет на основе указанного со скидкой в заданное число `%`, одновременно увеличив цену исходного билета на ту же сумму |
| 5 | Отменить указанное событие, удалив все билеты на него |

> [!NOTE]
> Все перечисленные операции реализуются **функциями базы данных** и вызываются
> с уровня бизнес-логики приложения.

## Хранение данных

- Данные об объектах хранятся в реляционной СУБД **PostgreSQL**;
  каждый объект, с которым работает ИС, сохраняется в базе.
- Все ограничения на поля класса (указанные в комментариях к описанию классов)
  реализуются **и на уровне ORM, и на уровне БД**.
- Поле `id` генерируется средствами базы данных.

### Подключение к БД на кафедральном сервере

| Параметр | Значение |
| --- | --- |
| Хост | `pg` |
| База данных | `studs` |
| Пользователь | совпадает с логином для подключения к серверу |
| Пароль | совпадает с паролем для подключения к серверу |

## Требования к интерфейсу

- Система реагирует на некорректный ввод: блокирует недопустимые значения
  и выводит **информативные сообщения об ошибках** с указанием причины.
- Переходы между логически обособленными частями системы выполняются через **меню**.
- Пользователи имеют возможность просматривать **все** объекты системы.

## Архитектурные требования

- Основа реализации — **Jakarta EE**.
- Уровень хранения — **JPA + Hibernate**.
- Уровни приложения **отделены друг от друга**, логические части вынесены
  в отдельные компоненты.

## Импорт объектов из файла

В систему добавляется возможность **массового добавления объектов** через загрузку
файла. Файл загружается на сервер через интерфейс веб-приложения.

> Формат файла для импорта необходимо **согласовать с преподавателем**.

Требования к логике импорта:

- **Атомарность.** Операция выполняется в транзакции: при возникновении любой ошибки
  не должен быть создан **ни один** объект.
- **Валидация.** Проверка пользовательского ввода выполняется в соответствии
  с ограничениями предметной области из ЛР1.
- **Вложенные объекты.** Значения полей вложенных объектов задаются
  в той же записи файла, что и основной объект.

## Ограничения уникальности

В модель из ЛР1 добавляются новые ограничения уникальности.

> Эти ограничения реализуются **исключительно на программном уровне** — в рамках
> бизнес-логики приложения. Они **не должны** быть отражены или продублированы в БД.

## Нагрузочный сценарий Apache JMeter

Реализуется сценарий, имитирующий **одновременную работу нескольких пользователей**
с ИС, для проверки корректности изоляции используемых транзакций.

### Покрытие сценария

- Создание объектов
- Редактирование объектов
- Удаление объектов
- Импорт объектов

### Проверяемые ситуации

| Ситуация | Что проверяется |
| --- | --- |
| Несколько пользователей обновляют и/или удаляют **один и тот же объект** (например, два администратора) | Корректность поведения системы при конкурентной модификации |
| Несколько пользователей одновременно создают объект с **одним и тем же уникальным значением** | Соблюдение ограничений уникальности предметной области |

### Результат исследования

По итогам наблюдения за поведением системы под нагрузкой необходимо **изменить
уровень изоляции транзакций** там, где это требуется, и **обосновать** каждое
изменение.

## Распределённая транзакция

Сохранение файла в хранилище должно быть **транзакционным по отношению**

> Для реализации распределённой транзакции разрешается использовать любые
> инструменты. **Рекомендуется** собственная реализация **двухфазного коммита (2PC)**
> на уровне бизнес-логики приложения.

## Как запустить

#### Бэк

> Версии везде указаны фиксированные, на них проводилась разработка

#### Шаг 1. Скачать Wildfly

```bash
wget https://github.com/wildfly/wildfly/releases/download/35.0.1.Final/wildfly-35.0.1.Final.zip
unzip wildfly-35.0.1.Final.zip
```

##### Шаг 1.1. Настроить порты

Так как порты по умолчанию, как правило, заняты, из следует поменять. Для этого в конце файла
`wildfly-35.0.1.Final/standalone/configuration/standalone.xml` нужно заменить как минимум порты `http` и `managed-http`.
Также можно опционально поменять и `https` порты, чтобы было меньше предупреждений при запуске.

```xml

<socket-binding-group name="standard-sockets" default-interface="public"
                      port-offset="${jboss.socket.binding.port-offset:0}">
    ...
    <socket-binding name="http" port="${jboss.http.port:8787}"/>
    <socket-binding name="https" port="${jboss.https.port:8788}"/>
    <socket-binding name="management-http" interface="management" port="${jboss.management.http.port:9595}"/>
    <socket-binding name="management-https" interface="management" port="${jboss.management.https.port:9596}"/>
    ...
</socket-binding-group>
```

#### Шаг 2. Скачать драйвер postgres

```bash
wget https://jdbc.postgresql.org/download/postgresql-42.7.7.jar
```

#### Шаг 3. Настроить модуль с драйвером

Для этого нужно в папку `wildfly-35.0.1.Final/modules/org/postgresql/main` положить jar с драйвером postgresql и рядом с
ним разместить файл [module.xml](config/module.xml)

> Папки `org/postgresql/main` нет по умолчанию, её нужно создать

#### Шаг 4. Выполнить конфигурацию Wildfly

Запускам wildfly

```bash
cd wildfly-35.0.1.Final
.wildfly-35.0.1.Final/bin/standalone.sh
```

Выполняем скрипт конфигурации, используя файл [configure-wildfly.cli](config/configure-wildfly.cli)

> ВАЖНО, порт 9595 это managed порт указанный в шаге 1.1

```bash
./bin/jboss-cli.sh --connect --controller=localhost:9595 --file=configure-wildfly.cli
```

В файле нужно не забыть изменить данные для подключения к бд:

```text
--connection-url=jdbc:postgresql://localhost:5432/pgdev \
--user-name=postgres \
--password=password \
```

#### Шаг 5. Загрузить схему БД

Используя файл со схемой [schema.sql](sql/schema.sql) загрузить схему

> Не забыть поменять данный подключения

```bash
psql -h localhost -U USERNAME -d DATABASE -f schema.sql
```

Опционально можно загрузить начальные данные, из файла [data.sql](sql/data.sql)

```bash
psql -h localhost -U USERNAME -d DATABASE -f data.sql
```

#### Шаг 6. Собрать war файл

```bash
./gradlew war
```

### Шаг 7. Деплой приложения

> Перед выполнением этой команды wildfly должен быть запущен

```bash
./bin/jboss-cli.sh --connect --controller=localhost:9595 --command="deploy is-labs-1.0.war --force"
```

### Фронт

#### Шаг 1. Скомпилировать фронт в статику

```bash
npm run build
```

Всё содержимое полученной папки dist нужно разместить в папке `frontend/www`

#### Шаг 2. Настроить конфигурацию Apache HTTP server

Рядом с папкой `www` нужно разместить файл [httpd.conf](config/httpd.conf)

При этом важно не забыть изменить следующие части файла:

- Порт на котором будет крутиться фронт

    ```text
    Listen 8585
    ```

- Все вхождения `/home/studs/s408850/is-lab/frontend` нужно заменить на абсолютный путь до своей корневой папки фронта

- Настроить параметры проксирования

    ```text
    ProxyPass        /api http://127.0.0.1:8787/is-labs-1.0
    ProxyPassReverse /api http://127.0.0.1:8787/is-labs-1.0
    
    ProxyPass        /ws ws://127.0.0.1:8787/is-labs-1.0
    ProxyPassReverse /ws ws://127.0.0.1:8787/is-labs-1.0
    ```
  
    - `8787` - порт `http` из wildfly
    - `/api` - это адрес по которому будет обращаться фронт для обычных запросов
    - `/ws` это адрес по которому будет обращаться фронт для работы веб-сокетами

### Шаг 3. Запустить Apache HTTP server

```bash
httpd -f ~/is-lab/frontend/httpd.conf -k start
```

Для остановки нужно выполнить

```bash
httpd -f ~/is-lab/frontend/httpd.conf -k stop
```
